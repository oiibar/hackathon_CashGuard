# CashGuard

Сервис для кейса ForteBank (Datathon 26). На вход — видео с камеры кассы, на выходе — список
моментов, которые стоит посмотреть проверяющему: таймкод, один–три кадра, что видно в кадре,
почему это может быть нарушением и пункт акта НБРК с дословной цитатой.

Всё работает на своём сервере, без облачных моделей и API. Лица не распознаются, звук не
используется. Ответ сервиса — подсказка для проверяющего, а не вывод о нарушении.

| | |
|---|---|
| Интерфейс | `https://<адрес>/?key=<ключ>` |
| API | `POST /api/v1/analyze`, `GET /api/v1/jobs/{job_id}`, ключ в заголовке `X-API-Key` |
| Документация API | `https://<адрес>/docs` |
| Метрики модели | вкладка «Качество модели» или `GET /api/v1/model` |

## Запуск по шагам

Нужен только Docker. Python и Node ставить не надо, всё собирается внутри образа.

**1. Установите Docker.** Windows и macOS — Docker Desktop, Linux — Docker Engine с плагином
compose. На Windows в настройках Docker Desktop (Resources) дайте не меньше 6 ГБ памяти.
Проверка:

```bash
docker --version
docker compose version
```

**2. Скачайте проект** и перейдите в папку:

```bash
git clone <адрес репозитория> cashguard
cd cashguard
```

**3. Создайте файл `.env`** с ключом API и паролем базы. Подойдут любые случайные строки:

```bash
echo "API_KEY=$(openssl rand -hex 16)" > .env
echo "POSTGRES_PASSWORD=$(openssl rand -hex 16)" >> .env
```

Если `openssl` нет (Windows), создайте `.env` в блокноте:

```
API_KEY=придумайте-длинный-ключ
POSTGRES_PASSWORD=придумайте-пароль
```

**4. Соберите и запустите.** Первая сборка скачивает модели и занимает 10–20 минут, образ
около 4,5 ГБ. Дальше сервис работает без интернета.

```bash
docker compose up -d --build
```

**5. Проверьте, что сервис поднялся.** Через минуту после старта:

```bash
curl http://localhost:8000/api/v1/health
```

В ответе `"status": "ok"`, `"storage": "postgres"` и номер версии модели. Если пусто — смотрите
логи: `docker compose logs -f cashguard`.

**6. Откройте интерфейс:** http://localhost:8000. Нажмите «Дополнительно», вставьте `API_KEY`
из `.env` (или откройте `http://localhost:8000/?key=<ключ>`, ключ подставится сам).
Перетащите `.mov` и нажмите «Начать анализ». Обработка занимает от 20 секунд до 3 минут.

**7. Подтвердите результат.** Под отчётом есть карточка «Проверка человеком»: отметьте, есть
ли нарушение, и если есть — секунду и тип. Эти ответы модель использует для дообучения
(подробно ниже).

**8. Публичный адрес для жюри** (по желанию). Туннель Cloudflare без регистрации и открытых
портов:

```bash
docker compose --profile public up -d
docker compose logs tunnel | grep -o 'https://[a-z0-9-]*\.trycloudflare\.com'
```

Туннель только пробрасывает HTTP, видео обрабатывается у вас. Адрес меняется при перезапуске
туннеля.

**Остановить:** `docker compose down`. Данные сохраняются: база в томе `pgdata`, кадры и
модели в папке `data/`. Удалить всё вместе с базой: `docker compose down -v`.

## Как это работает

```
браузер / API ──POST /analyze──► FastAPI ──job_id──► клиент
                                   │ очередь asyncio, задачи и отчёты в PostgreSQL
                                   ▼
1. detect   ffmpeg, до 4 кадров/с ─► YOLOv8n (люди, телефоны, сумки, ноутбук) + YOLO-World (деньги)
2. prepare  убрать людей за стеклом и дубли рамок, найти рабочее место кассира,
            увеличить стол и поискать мелкие предметы, CLIP-эмбеддинги 2 раза в секунду
3. judge    правила (rules.yaml) ─┐
            обученная модель ─────┴─► эпизоды ─► кадры-доказательства ─► отчёт
                                   ▼
проверяющий подтверждает вердикт ─► reviews ─► переобучение ─► новая версия модели
```

**Правила** проверяют то, что можно измерить: где человек, что у него в руках, сколько секунд.
Каждое срабатывание объяснимо. Оставлены только правила, которые не шумят на датасете:
телефон в руках кассира, второй посетитель у стола, кассир ушёл от ожидающего клиента, камера
перекрыта.

**Обученная модель** смотрит на сцену целиком. Каждые полсекунды считаем CLIP-эмбеддинг всего
кадра и увеличенного стола и вычитаем медиану по этому же ролику. Остаётся не «какая это
комната», а «что поменялось»: появилась сумка, открылся сейф, вошёл человек. Поверх —
стандартизация, PCA и логистическая регрессия. Тип эпизода берётся по ближайшему размеченному
примеру. Если в тот же момент сработало правило, в отчёт идёт правило: оно точнее объясняет,
что видно.

**Рабочее место ищется само.** Видео приходят без разметки, финальное снято под другим углом.
Кассир — тот, кто сидит на одном месте большую часть ролика, с поправкой на размер человека,
чтобы сотрудник за стеклянной стеной не стал «кассиром».

**Лимит 5 минут.** Дедлайн считается от загрузки. Частота кадров подбирается под длину видео и
скорость машины, при нехватке времени прореживаются кадры, увеличение и эмбеддинги. Если время
всё равно кончилось, отчёт строится по обработанной части (`meta.coverage`). Самый длинный
ролик датасета (142 с) обрабатывается за 171 с на обычном CPU.

| Модель | Лицензия | Зачем |
|---|---|---|
| YOLOv8n | AGPL-3.0 | люди, телефоны, сумки, ноутбук |
| YOLO-World v2-s, словарь «banknote, money, smartphone» | AGPL-3.0 | деньги и телефоны без дообучения |
| CLIP ViT-B/32 | MIT | эмбеддинги сцены |
| `violation_clf` | наша | PCA + логистическая регрессия, 200 КБ, обычный numpy |

## Дообучение на новых видео

Новое видео само по себе модель ничему не учит: у него нет разметки. Разметку даёт
проверяющий — карточка «Проверка человеком» под отчётом или `POST /jobs/{id}/review`.

1. При анализе эмбеддинги видео сохраняются в `data/embeddings/<job_id>.npz` (около 1 МБ на
   минуту видео). Само видео после обработки удаляется.
2. Ответ проверяющего пишется в таблицу `reviews`: есть нарушение или нет, секунда, тип.
3. Когда набирается `RETRAIN_MIN_REVIEWS` (по умолчанию 3) новых ответов, в фоне запускается
   переобучение. Если в этот момент обрабатываются видео, оно ждёт, чтобы не съесть их
   пятиминутный бюджет. Кнопка «Переобучить сейчас» на вкладке «Качество модели» запускает его
   вручную.
4. Обучающая выборка — исходные 42 ролика (`backend/models/base_set.npz`) плюс все
   подтверждённые видео.
5. Новая модель сравнивается с текущей и включается, только если выполнены все условия:
   - MCC на кросс-валидации не ниже текущей больше чем на 0,03;
   - recall не упал больше чем на 0,05;
   - на новых подтверждённых видео, которых текущая модель не видела, новая угадывает вердикт
     не реже текущей.
6. Каждая попытка — строка в `model_versions` с метриками и причиной решения, веса — файл в
   `data/models/`. Отклонённые версии тоже сохраняются. Откат — кнопка «Включить» у любой
   версии или `POST /model/versions/0/activate` для исходной.

**Как не переобучить и не недообучить.** Данных мало, поэтому всё решает валидация:

- **Кросс-валидация по роликам.** Все моменты одного видео лежат в одном фолде, иначе соседние
  кадры одного ролика попадали бы и в обучение, и в проверку, и цифры были бы завышены.
  Фолды стратифицированы по вердикту.
- **Сложность подбирается, а не задаётся.** Сетка: размер PCA k ∈ {8, 16, 32, 64} и сила
  регуляризации C ∈ {0,01; 0,1; 1}. Маленькое k и сильная регуляризация — недообучение, большое
  k и слабая — переобучение. Выбирается точка с лучшим MCC на отложенных видео.
- **Порог выбирается на отложенных оценках,** а не на обучающих.
- **Каждое видео весит одинаково.** Двухминутный ролик не перевешивает десятисекундный.
- **Диагностика в отчёте:** ROC-AUC по моментам на обучении и на отложенных видео. Разрыв больше
  0,15 — признак переобучения, отложенный AUC ниже 0,65 при низком обучающем — недообучения.
- **Ворота перед включением** (п. 5) не дают ухудшить работающую модель.

Тестовые видео жюри по условиям кейса нельзя использовать для обучения. Сервис и не учится на
них сам: в обучение попадает только то, что человек явно подтвердил. Если это нужно исключить
совсем, поставьте `LEARNING_ENABLED=false` — тогда эмбеддинги не сохраняются.

## Метрики

Все цифры посчитаны на видео, которые модель не видела при обучении: 10 фолдов по роликам.
Вердикт по видео, как у жюри. Обновляются после каждого переобучения, видны на вкладке
«Качество модели».

**Сервис целиком** (`backend/models/system_metrics.json`, считает `ml/evaluate.py`):

| Вариант | Верный вердикт | Recall | Ложные тревоги | Precision | F1 | MCC | Медиана ошибки таймкода |
|---|---|---|---|---|---|---|---|
| Всегда «нарушение» (базовая линия) | 22/42 | 22/22 | 20/20 | 52% | 0,69 | 0,00 | — |
| Только правила | 20/42 | 4/22 | 4/20 | 50% | 0,27 | −0,02 | 2,5 с |
| Только обученная модель | 27/42 | 21/22 | 14/20 | 60% | 0,74 | 0,34 | 5,0 с |
| **Правила + модель (в сервисе)** | **26/42** | **21/22** | **15/20** | **58%** | **0,72** | **0,29** | **4,5 с** |

Правила на вердикт почти не влияют: из 22 нарушений они находят 4, и все 4 модель находит и
так, а на чистых роликах добавляют одну ложную тревогу. Мы их оставили, потому что их эпизоды
объяснимы до пикселя («телефон в руке 3,2 с») и точнее по времени: медиана 2,5 с против 5 с у
модели. Когда эпизод нашли и правило, и модель, в отчёт идёт правило.

**Обученная модель отдельно:**

| Метрика | Значение | Что значит |
|---|---|---|
| Recall | 21/22 (95%) | доля роликов с нарушением, где модель его нашла |
| Precision | 60% | доля флагов, которые оказались настоящими |
| Ложные тревоги | 14/20 (FPR 70%) | чистые ролики, отмеченные как нарушение |
| F1 | 0,74 | баланс precision и recall |
| MCC | 0,34 | корреляция с разметкой; 0 — случайно, 1 — идеально; не обманывается перекосом классов |
| ROC-AUC по видео | 0,59 | насколько оценка видео отделяет нарушения от чистых, без порога |
| PR-AUC | 0,60 | то же для класса «нарушение» |
| ROC-AUC по моментам | 0,61 на отложенных, 0,76 на обучении | разрыв 0,15 — на границе переобучения |
| Brier | 0,30 | средний квадрат ошибки оценки; ниже — лучше |
| Медиана ошибки таймкода | 5,0 с (MAE 10,0 с) | по найденным нарушениям |
| Таймкод в пределах 3 с / 5 с | 33% / 57% | |
| Точный тип нарушения | 0/22 | 10 из 22 попадают на соседний тип с той же нормой |

Почему эти метрики. Вердикт бинарный, классы почти поровну (22/20), поэтому одна accuracy
мало говорит: «всегда нарушение» даёт 52%. Recall важен по FAQ кейса — пропуск хуже ложной
тревоги, ложные тревоги отдельно считаем в штуках. MCC выбран главным критерием отбора модели:
он единственный из стандартных не растёт на вырожденном ответе «всё нарушение». ROC-AUC и
PR-AUC показывают качество оценки без привязки к порогу. Таймкод — ошибка в секундах (критерий
2 жюри). R² здесь не подходит: это метрика регрессии, а у нас классификация; для таймкода
честнее средняя и медианная ошибка в секундах.

Цифры скромные. Модель почти всегда находит нарушение, но и на чистых роликах часто поднимает
флаг: ROC-AUC 0,59 значит, что одной оценкой сцены нарушения отделяются слабо. Основная причина
— 22 нарушения на 13 разных ситуаций, большинство встречается один-два раза. Дообучение на
подтверждённых видео нужно как раз для этого.

## Датасет

42 ролика (`ml/videos`, разметка `ml/open_labels.xlsx` → `ml/labels.csv`): 22 с нарушением,
20 без. Одна комната, камера сверху и из-за спины кассира, 464×848, от 11 до 143 секунд. Мы
пересмотрели все ролики и записали, что видно в момент из разметки (`ml/violation_types.csv`):

| Ситуация | Ролики |
|---|---|
| Кассир уходит, рабочее место открыто (ноутбук не заблокирован, сейф не заперт) | Х-11, Х-22, Х-24, Х-28 |
| Деньги или инкассаторская сумка остаются открыто на столе | Х-4, Х-15, Х-26 |
| В помещение кассы входит посторонний | Х-30, Х-33, Х-38 |
| Пересчёт купюр руками, скрытно от клиента | X-1, Х-47 |
| Личные вещи, еда на рабочем месте | Х-40, Х-46 |
| Телефон в руках кассира | X-2 |
| Второй посетитель подходит к столу во время операции | Х-18 |
| Сейф остаётся открытым | Х-20 |
| Дверь кассы оставлена открытой | Х-32 |
| Купюры подносятся к карману | Х-13 |
| Инкассатор передаёт сумку и уходит без проверки | Х-17 |
| Клиент уходит, не дождавшись пересчёта | Х-34 |

Почти у каждого нарушения есть «правильный двойник» среди чистых роликов. В Х-28 кассир
уходит с открытой таблицей на ноутбуке, в Х-29 та же сцена, но компьютер заблокирован.
Разница — двадцать пикселей экрана.

## Нормативная база

Только акты РК, тексты сверены с действующими редакциями на adilet.zan.kz (с изменениями по
постановлениям НБРК № 25 от 16.03.2026 и № 78 от 30.06.2026).

1. Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей
   в БВУ, постановление Правления НБРК от 29.11.2019 № 231 —
   https://adilet.zan.kz/rus/docs/V1900019680
2. Правила организации охраны и устройства помещений БВУ, постановление Правления НБРК от
   24.02.2020 № 14 — https://adilet.zan.kz/rus/docs/V2000020075. Пункт 16 приостановлен до
   01.01.2027 и действует во временной редакции, в ссылках это указано.

У каждого типа нарушения в `backend/config/rules.yaml` три текста: `observed` — что видно в
кадре, с числами из эпизода; `why` — почему это может быть нарушением; `quote` — дословный
текст пункта. Ссылаемся только на пункт, который прямо говорит о наблюдаемом действии.

| Тип | Пункт |
|---|---|
| Рабочее место оставлено открытым; наличные или сумка открыто; сейф открыт | № 231, п. 20 |
| Пересчёт денег вне поля зрения клиента | № 231, п. 20; п. 31 пп. 4) |
| Пересчёт без контролирующего работника | № 231, п. 42 |
| Клиент ушёл, не дождавшись пересчёта | № 231, п. 35 |
| Приём инкассаторской сумки без проверки | № 231, п. 24 пп. 3)–4); п. 25 |
| Телефон, личные вещи, деньги к карману | № 231, п. 12 |
| Кассир ушёл от ожидающего клиента | № 231, п. 22 |
| Посторонний в помещении кассы; дверь кассы открыта | № 14, п. 8; п. 16 пп. 1) |
| Второй посетитель во время обслуживания | № 231, п. 20 |
| Камера перекрыта | № 14, п. 16 пп. 6) |

Чего в актах нет, на то не ссылаемся: общего запрета «посторонним у кассы», запрета есть на
рабочем месте, запрета «оставлять сейф открытым» как такового. Для таких ситуаций выбран
ближайший пункт, и в `why` написано, почему он подходит. В текстах нет слов «кассир нарушил»,
только «может указывать на нарушение».

## Известные ошибки и ограничения

- **Ложные тревоги на «правильных уходах».** Модель видит, что кассир уходит, но плохо видит,
  запер ли он сейф и заблокировал ли ноутбук. Чистые Х-12, Х-23, Х-27, Х-29, Х-31 она отмечает.
- **Редкие типы почти не ловятся.** Пересчёт без контролёра, еда на столе, сумка — по одному
  примеру. Тип по ближайшему примеру для таких случаев угадать нельзя.
- **Тип на новом видео почти всегда неточный.** Тип берётся по ближайшему размеченному
  примеру, и на отложенных роликах точного попадания нет ни разу (0/22). В 10 случаях из 22
  модель называет соседний тип с той же нормой («наличные открыто» вместо «рабочее место
  открыто», оба — п. 20 Правил № 231). Вердикт и таймкод от этого не зависят.
- **Телефон и веер купюр** сверху выглядят одинаково, поэтому правило про телефон срабатывает
  и на пересчёт (Х-3, Х-14, Х-19, Х-45). В описании написано «предмет, похожий на телефон».
- **Одна комната.** Вычитание «нормального состояния» ролика должно помогать на другом ракурсе,
  но проверить это на данных было не на чем.
- **Дообучению нужны люди.** Без подтверждений модель не меняется. Плохие подтверждения
  ворота частично отсекут (новая версия не включится, если стала хуже), но не полностью.

Сервис не проверяет проводки, сверки, пломбы и полномочия людей, не определяет личность и не
использует звук.

## База данных

PostgreSQL 16, схема создаётся при старте (`backend/app/store.py`), миграции не нужны: все
`CREATE … IF NOT EXISTS`.

| Таблица | Что хранит |
|---|---|
| `jobs` | задача: файл, статус, вердикт, ошибка, `meta` (JSONB), время создания и окончания |
| `violations` | нарушения задачи: тип, таймкод, описание, нормы (JSONB); `ON DELETE CASCADE` от `jobs` |
| `evidence_frames` | путь к JPEG-кадру и его секунда; сами кадры в `data/evidence/<job_id>/` |
| `reviews` | ответ проверяющего: вердикт, секунда, тип, какая версия модели на нём обучилась |
| `model_versions` | версии модели: статус (`active`, `retired`, `rejected`), параметры, метрики, причина решения |

Ограничения на уровне базы: статусы и вердикты — `CHECK`; у ответа «нарушение» обязательна
секунда; активной может быть только одна версия (частичный уникальный индекс). Картинки в
базе не хранятся: base64 раздул бы каждую строку на сотни килобайт.

Без `DATABASE_URL` сервис пишет всё в JSON-файлы — так работают тесты и быстрый запуск без
Postgres.

## Обучение с нуля

Нужны видео датасета в `ml/videos`. Команды запускаются в контейнере сервиса с проектом,
смонтированным в `/repo`:

```bash
docker compose run --rm -v "$PWD:/repo" -w /repo cashguard sh
python ml/evaluate.py ml/videos ml/labels.csv --fresh   # детекции, кэш в ml/cache, метрики сервиса
python ml/train_classifier.py                           # эмбеддинги, кросс-валидация, base_set.npz и веса
python ml/evaluate.py ml/videos ml/labels.csv           # пересчитать метрики с новой моделью
python ml/inspect_scene.py Х-28 --from 5 --to 12        # что видят правила, кадр за кадром
```

`--folds 0` у `train_classifier.py` включает leave-one-video-out вместо 10 фолдов.

## Настройки

| Переменная | По умолчанию | |
|---|---|---|
| `API_KEY` | `change-me` | ключ для `X-API-Key` |
| `DATABASE_URL` | задаёт compose | без неё — JSON-файлы |
| `LEARNING_ENABLED` | `true` | сохранять эмбеддинги и учиться на подтверждениях |
| `AUTO_RETRAIN` | `true` | переобучать автоматически |
| `RETRAIN_MIN_REVIEWS` | `3` | сколько новых подтверждений запускает переобучение |
| `CV_FOLDS` | `10` | фолды кросс-валидации, `0` — leave-one-video-out |

| `TARGET_FPS` / `MIN_FPS` | `4` / `0.5` | частота анализа |
| `JOB_DEADLINE_SEC` | `270` | бюджет задачи от загрузки |
| `WORKERS` | `1` | параллельные обработчики |
| `KEEP_VIDEOS` | `false` | хранить видео после обработки |
