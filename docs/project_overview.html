1. Summary

Problem. Bank cash operations are recorded on video, but reviewing hours of footage by hand is slow. ForteBank asked for a service that a bank employee can upload a video to and get back: a verdict (“no violation found” or “signs of possible violations”), and for every finding its type, timecode, 1–3 evidence frames, a plain description of what is visible and a reference to a Kazakhstan regulation. The service must run fully on premises, answer through a keyed API within 5 minutes per video, and cope with a different camera angle at the final.

What we built. A FastAPI service with a React interface and PostgreSQL storage, packaged as two Docker containers. Every video goes through three stages: object detection (YOLOv8n and YOLO-World), scene preparation (finding the cashier’s workplace, zooming into the desk, CLIP scene embeddings) and judgement, where explainable rules and a trained scene classifier produce episodes. Each episode is matched to a clause of NBRK Resolution No. 231 or No. 14 with a verbatim quote. Reviewers confirm or correct each verdict; those answers retrain the model, and a new version only goes live if it is not worse on held-out data.

Key results (all measured on videos excluded from training, 10 folds grouped by video):

  • Whole service: 26 of 42 verdicts correct, recall 21/22 (95%), 15 false alarms out of 20 clean videos, MCC 0.29, median timecode error 4.5 s.
  • Trained model alone: 27/42, recall 95%, precision 60%, ROC-AUC 0.59, MCC 0.34. Calibration cut the expected calibration error from 0.24 to 0.08.
  • The service rarely misses a violation, which the case FAQ calls unacceptable, but it raises too many false alarms. The main cause is data: 22 violations spread over 13 different situations. The learning loop exists to fix this.

4. Architecture

Two containers started by docker compose: cashguard (Python service with the built React app) and db (PostgreSQL 16, not exposed outside the compose network). An optional third container runs a Cloudflare quick tunnel to give the jury a public HTTPS address without opening ports; it only forwards HTTP, all processing stays local.

5. Machine learning

5.1 Data

42 staged videos from one room, overhead camera behind the cashier, 464×848, 11–143 s: 22 with a violation and a labelled second, 20 clean. Types are not given; we watched every video and wrote down what happens at the labelled moment (ml/violation_types.csv): 13 situations, most with one or two examples, and nearly every violation has a near-identical clean “twin”.

5.2 Detection and scene

  • YOLOv8n (COCO) for people, phones, handbags, laptops and screens; YOLO-World v2-s with a fixed vocabulary (“banknote, money, smartphone”) for cash without fine-tuning. Detections are merged by class name.
  • Workplace inference. The cashier is the person who stays in one place for most of the video. A 24×24 occupancy grid weighted by box size finds that place; the cashier zone is the median box, kept tight because the client appears directly above the cashier from this camera.
  • Desk zoom. The desk is cropped, enlarged and run through the detector again for small objects.
  • Fixtures. Objects that never move (card terminal, calculator) are dropped so they don’t read as phones.

5.3 Trained scene model

Twice a second we take a CLIP ViT-B/32 embedding of the whole frame and of the desk crop and subtract the median embedding of the same video, which leaves “what changed” rather than “which room”. Features are the change itself, its ±1 s average and its 2-second difference (2,048 numbers). A standard scaler, PCA and an L2-regularised logistic regression score each moment. Training moments: label −1 s … +2 s as positive; clean videos and moments more than 5 s before the label as negative; each video weighs the same.

5.4 Validation, overfitting and underfitting

  • Grouped cross-validation. 10 folds, all moments of one video in one fold, stratified by verdict. Splitting moments randomly would put neighbouring frames of one video in both training and test and inflate every metric.
  • Model complexity chosen by data. Grid over PCA size k ∈ {8, 16, 32, 64} and regularisation C ∈ {0.01, 0.1, 1}; the best held-out MCC wins (k = 16, C = 0.1). k = 8 underfits, k = 64 overfits.
  • Threshold chosen on held-out scores, by MCC by default or by lowest error cost (THRESHOLD_POLICY=cost).
  • Diagnostics. Moment-level ROC-AUC on training 0.76 vs held-out 0.61: a gap of 0.15, right at our overfitting line; it is reported, not hidden.
  • Calibration. Platt scaling on held-out video scores, applied only if it improves the leave-one-out ECE. It did: 0.24 → 0.08, so the confidence field is a calibrated probability.

6. Continuous learning

  1. Every processed video leaves its CLIP embeddings in data/embeddings (≈1 MB per minute); the video itself is deleted.
  2. The reviewer’s answer is stored in reviews (violation or not, second, type).
  3. After RETRAIN_MIN_REVIEWS = 3 new answers, retraining starts in the background, waiting until no video is in processing so the 5-minute budget is never affected. It took about 20 s on CPU in our test.
  4. Training set: the 42 dataset videos (backend/models/base_set.npz) plus all confirmed videos. Same grouped CV, grid, threshold and calibration as offline.
  5. Promotion gate: held-out MCC may not drop by more than 0.03, recall may not drop by more than 0.05, and on the newly reviewed videos (unseen by the current model) the challenger must be at least as accurate.
  6. Every attempt, promoted or rejected, is a row in model_versions with metrics and the reason; any version can be re-activated, version 0 is the shipped model.
Live test: three confirmed videos produced a challenger with higher MCC (0.38) but recall dropping from 95% to 67%. The gate rejected it and the previous model kept running, exactly as intended for a bank that treats a missed violation as unacceptable.

Other model metrics: specificity 0.30, FPR 0.70, FNR 0.05, ROC-AUC 0.59, PR-AUC 0.60, Brier 0.30 (0.26 calibrated), timecode within 3 s 33% / within 5 s 57%. Exact violation type on held-out videos: 0 of 22; in 10 of 22 the model names a neighbouring type that cites the same legal clause.

Why these metrics. The jury scores the verdict per video and the classes are nearly balanced (22/20), so accuracy alone says little: answering “violation” every time already gets 52%. MCC and Cohen’s kappa do not reward that degenerate answer, so MCC selects the model. Recall and F2 reflect the FAQ’s statement that a missed violation is unacceptable. ROC-AUC and PR-AUC measure ranking independent of the threshold. Timecode error in seconds measures criterion 2. R² is not used: it is a regression metric and the verdict is a classification.

7.2 Operating point and cost

The MCC threshold (0.606) gives 21/22 recall with 14 false alarms, cost 24. The cost-optimal threshold (0.579) catches all 22 with 16 false alarms, cost 16, at one less correct verdict overall. Which one to run is a bank decision, exposed as THRESHOLD_POLICY.

7.3 Robustness

Every dataset video was re-encoded with a distortion, re-embedded with CLIP and scored by the fold model that never saw it, at the production threshold.

ConditionRecallFPRROC-AUC
Clean (1 frame/s)0.910.750.59
Other angle (perspective + 7° rotation)0.860.800.60

The simulated angle change keeps ranking quality, which supports the per-video median subtraction. Heavy compression and occlusion drop it to chance. Training with the same distortions as augmentation was tested and rejected: it improved darkness and angle but cut clean-video recall to 0.64–0.86, unacceptable under the recall-first policy.

7.4 Subgroups

Protected attributes (gender, age, ethnicity) are neither in the data nor extracted, because face recognition is forbidden by the case. Demographic parity and equalised-odds gaps therefore cannot be computed honestly; doing so needs a separately consented labelling. As a substitute we split by shooting conditions: across brightness, video length and crowding terciles, the largest gap is 0.17 in recall and 0.43 in false-positive rate. The brightest third of videos has the most false alarms (FPR 0.88).

9. Legal basis

Only acts of the Republic of Kazakhstan, checked against the current editions on adilet.zan.kz:

  • Rules for cash operations and cash collection, NBRK Board Resolution No. 231 of 29.11.2019 (V1900019680).
  • Rules for security and premises of second-tier banks, NBRK Board Resolution No. 14 of 24.02.2020 (V2000020075); clause 16 is suspended until 01.01.2027 and applies in its temporary wording, which the references state.

Each violation type stores three separate texts: what is visible (with numbers from the episode), why it may be a violation (our wording), and the verbatim clause. All 18 types have a clause with quote and link. Where the acts have no direct prohibition (eating at the desk, an open safe as such), we cite the closest clause and explain the link instead of inventing one. The mapping is listed in the developer report as a register awaiting sign-off by the bank’s legal or compliance team.

11. Limitations

  • Many false alarms (15 of 20 clean videos). A “correct exit” differs from a violation by a locked laptop screen about 20 pixels wide.
  • Exact type on new videos is unreliable: 13 situations over 22 examples.
  • One room in the dataset: the different-angle behaviour is designed in and simulated, but not measured on real footage.
  • Phones and fanned banknotes look alike from the ceiling, so the phone rule fires on cash counting; the text says “an object that looks like a phone”.
  • Learning needs people: without reviews the model does not change, and wrong reviews are only partly caught by the gate.
  • The service cannot judge postings, reconciliations, seals or staff authority, and does not identify people.

13. Team split: four members

The work divides along four ownership areas with clear interfaces: the pipeline produces a report dictionary, the backend stores and serves it, the frontend renders it, and the domain owner defines what a violation is and how it is justified. Each member owns their files, reviews the neighbouring area, and presents their part at the pitch.

14. How to run

  1. Install Docker (Docker Desktop on Windows/macOS; give it at least 6 GB of memory).
  2. Clone the repository and create .env with API_KEY=… and POSTGRES_PASSWORD=….
  3. docker compose up -d --build — the first build downloads model weights (10–20 minutes, ~4.5 GB image).
  4. curl http://localhost:8000/api/v1/health should return "status": "ok".
  5. Open http://localhost:8000/?key=<API_KEY>, upload a .mov, wait for the report, confirm the verdict.
  6. Optional public address: docker compose --profile public up -d, then read the trycloudflare URL from docker compose logs tunnel.
  7. Tests: docker compose exec cashguard python -m pytest -q. Developer report: python ml/report.py inside the container with the repo mounted (see README).
